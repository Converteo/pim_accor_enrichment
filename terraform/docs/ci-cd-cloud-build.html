Guide débutant · CI/CD · cloudbuild.yaml de ce repo

Pousser du code, c’est déployer.

Plus de script à lancer depuis ton poste : quand du code arrive sur la branche dev ou stg de GitHub, Google Cloud Build construit l’application et la met en ligne tout seul. Ce guide explique comment, avec exactement la configuration de PIM Accor enrichment.

1. L’idée, en une image mentale

Reprenons l’hôtel. Le code sur GitHub, c’est la recette. Pousser sur dev, c’est envoyer un bon de commande en cuisine. Cloud Build, c’est la brigade : elle prépare le plat (construit l’image Docker), le range en chambre froide (Artifact Registry), puis le sert en salle (nouvelle version sur Cloud Run). Personne n’a besoin d’aller en cuisine.

Avant

Déploiement à la main
Un script lancé depuis un Mac : Docker, gcloud, Terraform installés, droits sur le projet, et on espère que tout le monde fait pareil.

→

Maintenant

CI/CD
Un git push. Le build se fait chez Google, toujours de la même façon, et il est tracé (qui, quel commit, quand).

CI (intégration continue) : construire et vérifier automatiquement chaque changement. CD (déploiement continu) : le mettre en ligne automatiquement.

2. Les branches : une par environnement

Chaque branche « longue » correspond à un environnement. Le code avance de gauche à droite :

feature/ma-modif ─PR→ dev ─PR→ stg ─PR→ main
BrancheQue se passe-t-il quand elle reçoit du code ?
feature/…Rien. C’est ton brouillon personnel.
devDéploiement automatique sur l’environnement dev : on vérifie que ça marche « en vrai ».
stgDéploiement automatique sur stg (staging) : la répétition générale, montrée au client.
mainRien pour l’instant. C’est la version de référence ; elle déploiera la production le jour où elle existera.

Une PR (pull request) est une demande de fusion sur GitHub : on montre ses changements, quelqu’un relit, puis on clique « Merge ». La fusion est un push sur la branche cible, donc elle déclenche le déploiement.

3. Le parcours d’un commit, de ton poste à l’URL

Push sur dev

Directement, ou en fusionnant une PR dans dev.

GitHub prévient Google

L’application GitHub « Google Cloud Build », installée sur l’organisation Converteo, signale le push à Cloud Build.

Le trigger se déclenche

Le trigger gcb-cvto-accor-pim-enrichment-dev-euw1-deploy écoute la branche dev. Il lance un build en lui passant les paramètres de dev (dépôt d’images, noms des Cloud Run…).

Cloud Build suit la recette

Il lit cloudbuild.yaml à la racine du repo : construire l’image, la pousser, déployer.

Nouvelle révision Cloud Run

Cloud Run démarre la nouvelle version, vérifie qu’elle répond, puis lui envoie 100 % du trafic. L’ancienne reste disponible pour revenir en arrière.

Retour dans GitHub

Le commit affiche une coche verte (réussi) ou une croix rouge (échec), avec un lien vers les logs.

Compte en général 3 à 5 minutes entre le push et la mise en ligne.

4. La recette : cloudbuild.yaml

Un build est une suite d’étapes (steps). Chaque étape tourne dans un petit conteneur outil (name : l’outil Docker, l’outil gcloud…). Voici les nôtres :

front-build→ front-push→ front-deploy
back-build-push→ back-deploy (en parallèle, seulement si backend/Dockerfile existe)
ÉtapeCe qu’elle fait
front-buildLance docker build sur le dossier frontend/ (le même Dockerfile que sur ton poste).
front-pushEnvoie l’image dans l’Artifact Registry de l’environnement, avec deux étiquettes : le commit (a1b2c3d) et l’env (dev).
front-deploygcloud run deploy : le Cloud Run front passe sur cette image.
back-…Même chose pour le backend, mais l’étape se saute elle-même tant qu’il n’y a pas de code backend.

Le même fichier sert pour dev et stg. Ce qui change vient du trigger, sous forme de substitutions (les variables qui commencent par _) :

# extrait de cloudbuild.yaml
- id: front-deploy
  name: gcr.io/google.com/cloudsdktool/cloud-sdk:slim
  entrypoint: gcloud
  args:
    - run
    - deploy
    - ${_FRONT_SERVICE}                              # gcr-cvto-accor-pim-enrichment-dev-euw1-front
    - --image=${_AR_PATH}/frontend:${SHORT_SHA}      # …/ar-…-dev-euw1-docker/frontend:a1b2c3d
    - --region=${_REGION}

SHORT_SHA est fourni par Cloud Build : ce sont les 7 premiers caractères du commit. Chaque image se rattache donc à un commit précis.

5. Qui fait quoi

ÉlémentNomRôle
App GitHub « Google Cloud Build » Installée sur l’org Converteo : elle autorise Google à voir le repo et à recevoir les pushs.
Connexion gcb-cvto-accor-pim-enrichment-euw1-github Le lien GitHub ↔ Cloud Build. Une seule pour le projet, partagée par dev et stg.
Token GitHub secret sec-cvto-accor-pim-enrichment-github-token Rangé dans Secret Manager, jamais dans le code. Seul l’agent Cloud Build peut le lire.
Triggers gcb-…-dev-euw1-deploy, gcb-…-stg-euw1-deploy « Quand la branche X reçoit un push, lance cloudbuild.yaml avec les paramètres de l’env X ».
SA de build sa-dev-cloudbuild, sa-stg-cloudbuild L’identité du build. Elle a le strict nécessaire, et uniquement sur son environnement.

Les droits du SA de build (ex. dev)

  • artifactregistry.writer sur le dépôt ar-…-dev-euw1-docker : pousser des images ;
  • run.developer sur les 2 Cloud Run dev : publier une nouvelle version ;
  • iam.serviceAccountUser sur sa-dev-frontend et sa-dev-backend : lancer les conteneurs avec leur identité ;
  • logging.logWriter : écrire les logs du build.

Conséquence : un build déclenché par dev ne peut pas toucher à stg, même par erreur. Il ne peut pas non plus modifier l’infrastructure (buckets, droits…).

6. CI et Terraform : qui possède quoi ?

Deux outils agissent sur les mêmes Cloud Run. Pour qu’ils ne se contredisent pas, on a partagé les rôles :

Terraform (à la main, rarement)

Construit l’hôtel
Services Cloud Run, buckets, droits, triggers, secret… Lancé avec make plan / make apply.

≠

Cloud Build (à chaque push)

Change le menu
Seulement l’image qui tourne dans les Cloud Run.

Dans le module cloud_run, Terraform crée le service avec une image de démarrage, puis ignore l’image : 

lifecycle {
  ignore_changes = [
    template[0].containers[0].image,   # gérée par Cloud Build
    client, client_version,
  ]
}

Sans ça, chaque make apply remettrait l’ancienne image et annulerait le dernier déploiement. C’est aussi pour ça qu’il n’y a plus de front_image_tag dans vars/*.tfvars, ni de script de déploiement.

Un push qui ne modifie que terraform/**, de la doc (*.md, docs/**), renovate.json ou docker-compose.yml ne lance pas de build (ignored_files du trigger). Inutile de redéployer l’application pour une modif de doc.

7. Au quotidien

Livrer une modification en dev

git checkout dev && git pull
git checkout -b feature/mon-changement
# … modifications, tests en local (npm run dev ou docker compose up) …
git commit -am "feat: mon changement"
git push -u origin feature/mon-changement
# sur GitHub : ouvrir une PR feature/mon-changement → dev, faire relire, Merge

Promouvoir dev vers stg

Sur GitHub, ouvrir une PR dev → stg, relire la liste des commits, Merge. stg se déploie avec exactement le même code que dev.

Suivre un build

  • Sur GitHub : l’icône à côté du commit (rond orange = en cours, coche verte, croix rouge), puis « Details ».
  • Dans la console GCP : Cloud Build › Historique (europe-west1).

Vérifier le résultat

EnvURL du front
devgcr-…-dev-euw1-front…run.app
stggcr-…-stg-euw1-front…run.app

8. En cas de problème

Le build est rouge

Rien n’a été mis en ligne : Cloud Run garde la version précédente. Ouvre les logs, trouve la première étape en échec. Le plus souvent c’est front-build : une erreur TypeScript ou une règle métier (npm run check) qui casse. Corrige, re-pousse.

Le build est vert mais l’appli est cassée

Deux façons de revenir en arrière :

  • La bonne : git revert du commit fautif puis push. L’historique reste propre et la CI redéploie l’ancienne version.
  • L’urgence : console Cloud Run › le service › Révisions › « Gérer le trafic » : remettre 100 % sur la révision précédente. Effet immédiat, mais le prochain push redéploiera la branche : il faut quand même corriger le code.

Ne pas déployer « à la main » avec gcloud run deploy depuis son poste : la version en ligne ne correspondrait plus à aucune branche, et le push suivant l’écraserait.

10. Glossaire

MotEn clair
BuildUne exécution de la recette cloudbuild.yaml.
TriggerLa règle « tel événement GitHub → tel build ».
ImageL’application emballée (code + Node.js + dépendances), prête à tourner n’importe où.
TagL’étiquette d’une image : ici le commit (a1b2c3d) et l’env (dev).
Artifact RegistryL’entrepôt d’images Docker du projet, un dépôt par env.
RévisionUne version figée d’un service Cloud Run. Chaque déploiement en crée une nouvelle.
SubstitutionVariable passée par le trigger au cloudbuild.yaml (_ENV, _FRONT_SERVICE…).
Service accountIdentité d’un programme (ici : le build, le front, le back), avec ses propres droits.
