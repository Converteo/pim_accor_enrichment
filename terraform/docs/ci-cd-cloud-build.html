Guide débutant · CI/CD · GitHub Actions + Cloud Build

Pousser du code, c’est déployer.

Plus de script à lancer depuis ton poste : quand du code arrive sur la branche dev ou stg de GitHub, l’application est construite par Google Cloud Build et mise en ligne toute seule. Ce guide explique comment, avec exactement la configuration de PIM Accor enrichment.

1. L’idée, en une image mentale

Reprenons l’hôtel. Le code sur GitHub, c’est la recette. Pousser sur dev, c’est déposer un bon de commande. GitHub Actions est le serveur qui porte le bon en cuisine. Cloud Build, c’est la brigade : elle prépare le plat (construit l’image Docker), le range en chambre froide (Artifact Registry), puis le sert en salle (nouvelle version sur Cloud Run).

Avant

Déploiement à la main
Un script lancé depuis un Mac : Docker, gcloud, Terraform installés, droits sur le projet, et on espère que tout le monde fait pareil.

→

Maintenant

CI/CD
Un git push. Le build se fait chez Google, toujours de la même façon, et il est tracé (qui, quel commit, quand).

CI (intégration continue) : construire et vérifier automatiquement chaque changement. CD (déploiement continu) : le mettre en ligne automatiquement.

2. Les branches : une par environnement

Chaque branche « longue » correspond à un environnement. Le code avance de gauche à droite :

feature/ma-modif ─PR→ dev ─PR→ stg ─PR→ main
BrancheQue se passe-t-il quand elle reçoit du code ?
feature/…Rien. C’est ton brouillon personnel.
devDéploiement automatique sur l’environnement dev : on vérifie que ça marche « en vrai ».
stgDéploiement automatique sur stg (staging) : la répétition générale, montrée au client.
mainRien pour l’instant. C’est la version de référence ; elle déploiera la production le jour où elle existera.

Une PR (pull request) est une demande de fusion sur GitHub : on montre ses changements, quelqu’un relit, puis on clique « Merge ». La fusion est un push sur la branche cible, donc elle déclenche le déploiement.

3. Le parcours d’un commit, de ton poste à l’URL

Push sur dev

Directement, ou en fusionnant une PR dans dev.

GitHub Actions démarre

Le workflow .github/workflows/deploy.yml écoute les branches dev et stg. Il récupère le code sur une machine éphémère fournie par GitHub.

Il s’authentifie auprès de Google, sans mot de passe

Il présente un jeton signé par GitHub (« je suis ce repo, branche dev ») et reçoit en échange un accès temporaire au compte sa-dev-cloudbuild. Voir la section suivante.

Il confie le travail à Cloud Build

gcloud builds submit envoie le code dans le bucket bkt-…-dev-euw1-build-sources et demande à Cloud Build d’exécuter cloudbuild.yaml avec les paramètres de dev.

Cloud Build construit et déploie

Image Docker, envoi dans l’Artifact Registry de dev, puis nouvelle révision du Cloud Run front (et back s’il existe).

Retour dans GitHub

Le commit affiche une coche verte (réussi) ou une croix rouge (échec). Les logs sont dans l’onglet Actions du repo et dans Cloud Build.

Compte en général 4 à 6 minutes entre le push et la mise en ligne.

4. La « clé sans clé » : Workload Identity Federation

Pour agir dans Google Cloud, GitHub Actions doit prouver qui il est. L’ancienne méthode consistait à copier une clé de compte de service (un fichier JSON) dans les secrets GitHub : si elle fuit, n’importe qui peut s’en servir, et elle n’expire jamais. Ici, aucune clé n’existe.

GitHub

Délivre un badge
À chaque exécution, un jeton signé, valable quelques minutes : « repo Converteo/pim_accor_enrichment, branche dev, événement push ».

→

Google Cloud

Vérifie le badge à l’accueil
Le « pool d’identités » gh-cvto-accor-pim-enrichment contrôle la signature et les règles, puis prête un accès temporaire.

Les règles du contrôle d’accès (définies dans Terraform)

  • seul ce repo est accepté, identifié par son numéro unique (un repo renommé ou recréé sous le même nom serait refusé) ;
  • seul un push est accepté : une pull request, même venant d’un fork d’un inconnu, ne peut rien déployer ;
  • la branche dev ne peut emprunter que sa-dev-cloudbuild, la branche stg que sa-stg-cloudbuild.

Résultat : rien à installer sur GitHub, aucun secret à stocker ni à renouveler, et même dans un repo public personne d’autre ne peut déclencher un déploiement.

5. Les deux fichiers de la CI

.github/workflows/deploy.yml : le déclencheur

Il dit quand déployer et où. Le nom de la branche donne l’environnement :

on:
  push:
    branches: [dev, stg]
    paths-ignore: ["terraform/**", "**/*.md", "**/docs/**", …]

# … authentification (WIF), puis :
gcloud builds submit . \
  --config=cloudbuild.yaml \
  --service-account=…/sa-${ENV}-cloudbuild@… \
  --substitutions=_ENV=${ENV},_TAG=${TAG},_FRONT_SERVICE=gcr-…-${ENV}-euw1-front,…

paths-ignore : un push qui ne modifie que l’infra ou la doc ne redéploie pas l’application. concurrency : deux pushs rapprochés sur dev sont déployés l’un après l’autre, jamais en même temps.

cloudbuild.yaml : la recette

Il dit comment construire et déployer. Chaque étape tourne dans un petit conteneur outil (Docker, gcloud) :

front-build→ front-push→ front-deploy
back-build-push→ back-deploy (en parallèle, seulement si backend/Dockerfile existe)
ÉtapeCe qu’elle fait
front-builddocker build du dossier frontend/ (le même Dockerfile que sur ton poste).
front-pushEnvoie l’image dans l’Artifact Registry de l’environnement, avec deux étiquettes : le commit (a1b2c3d) et l’env (dev).
front-deploygcloud run deploy : le Cloud Run front passe sur cette image.
back-…Même chose pour le backend, mais l’étape se saute elle-même tant qu’il n’y a pas de code backend.

Les variables qui commencent par _ (_ENV, _TAG, _FRONT_SERVICE…) sont des substitutions : le même fichier sert pour dev et stg, ce sont les valeurs envoyées par le workflow qui changent. _TAG vaut les 7 premiers caractères du commit : chaque image se rattache à un commit précis.

6. Qui fait quoi

ÉlémentNomRôle
Workflow GitHub .github/workflows/deploy.yml Se déclenche sur push dev / stg, s’authentifie, lance Cloud Build.
Pool d’identités gh-cvto-accor-pim-enrichment (fournisseur github) Vérifie les badges GitHub. Un seul pour le projet, géré par l’env dev dans Terraform.
SA de build sa-dev-cloudbuild, sa-stg-cloudbuild L’identité empruntée par le workflow, puis utilisée par Cloud Build. Strict nécessaire, sur son env.
Bucket de sources bkt-…-<env>-euw1-build-sources Zone de dépôt du code à construire. Vidé automatiquement après 7 jours.
Artifact Registry ar-…-<env>-euw1-docker Les images construites, une par commit déployé.

Les droits du SA de build (ex. dev)

  • cloudbuild.builds.editor : lancer un build ;
  • storage.objectAdmin sur le bucket de sources dev : y déposer le code ;
  • artifactregistry.writer sur le dépôt dev : pousser des images ;
  • run.developer sur les 2 Cloud Run dev : publier une nouvelle version ;
  • iam.serviceAccountUser sur sa-dev-frontend, sa-dev-backend et lui-même : lancer les conteneurs et le build avec ces identités ;
  • logging.logWriter / logging.viewer : écrire les logs du build et les afficher dans GitHub.

Conséquence : un push sur dev ne peut pas toucher aux Cloud Run de stg, même par erreur, et la CI ne peut pas modifier l’infrastructure (buckets de données, droits…).

7. CI et Terraform : qui possède quoi ?

Deux outils agissent sur les mêmes Cloud Run. Pour qu’ils ne se contredisent pas, on a partagé les rôles :

Terraform (à la main, rarement)

Construit l’hôtel
Services Cloud Run, buckets, droits, pool d’identités… Lancé avec make plan / make apply.

≠

La CI (à chaque push)

Change le menu
Seulement l’image qui tourne dans les Cloud Run.

Dans le module cloud_run, Terraform crée le service avec une image de démarrage, puis ignore l’image :

lifecycle {
  ignore_changes = [
    template[0].containers[0].image,   # gérée par la CI
    client, client_version,
  ]
}

Sans ça, chaque make apply remettrait l’ancienne image et annulerait le dernier déploiement. C’est aussi pour ça qu’il n’y a plus de tag d’image dans vars/*.tfvars, ni de script de déploiement.

8. Au quotidien

Livrer une modification en dev

git checkout dev && git pull
git checkout -b feature/mon-changement
# … modifications, tests en local (npm run dev ou docker compose up) …
git commit -am "feat: mon changement"
git push -u origin feature/mon-changement
# sur GitHub : ouvrir une PR feature/mon-changement → dev, faire relire, Merge

Promouvoir dev vers stg

Sur GitHub, ouvrir une PR dev → stg, relire la liste des commits, Merge. stg se déploie avec exactement le même code que dev.

Suivre un déploiement

  • Sur GitHub : onglet Actions du repo, ou l’icône à côté du commit (rond orange = en cours, coche verte, croix rouge).
  • Dans la console GCP : Cloud Build › Historique, région europe-west1.

Trouver l’URL de l’application

make output ENV=dev dans terraform/ (valeur front_url), ou console GCP › Cloud Run › gcr-…-dev-euw1-front.

9. En cas de problème

Le workflow est rouge

Rien n’a été mis en ligne : Cloud Run garde la version précédente. Ouvre le run dans l’onglet Actions et trouve la première étape en échec :

  • échec à « S’authentifier sur GCP » : souci de droits WIF (la branche n’est pas dev/stg, ou la config Terraform a changé) ;
  • échec dans « Construire et déployer » : ouvre le lien du build Cloud Build. Le plus souvent c’est front-build, à cause d’une erreur TypeScript ou d’une règle métier (npm run check). Corrige, re-pousse.

Le déploiement est vert mais l’appli est cassée

  • La bonne méthode : git revert du commit fautif puis push. L’historique reste propre et la CI redéploie l’ancienne version.
  • L’urgence : console Cloud Run › le service › Révisions › « Gérer le trafic » : remettre 100 % sur la révision précédente. Effet immédiat, mais le prochain push redéploiera la branche : il faut quand même corriger le code.

Ne pas déployer « à la main » avec gcloud run deploy depuis son poste : la version en ligne ne correspondrait plus à aucune branche, et le push suivant l’écraserait.

10. Glossaire

MotEn clair
GitHub ActionsLe moteur d’automatisation intégré à GitHub : exécute un workflow quand un événement arrive (ici, un push).
WorkflowLe fichier YAML qui décrit l’automatisation (.github/workflows/deploy.yml).
BuildUne exécution de la recette cloudbuild.yaml par Cloud Build.
Workload Identity FederationLe mécanisme qui laisse GitHub emprunter une identité Google sans clé ni mot de passe.
OIDCLe standard du « badge signé » que GitHub délivre à chaque exécution.
ImageL’application emballée (code + Node.js + dépendances), prête à tourner n’importe où.
TagL’étiquette d’une image : ici le commit (a1b2c3d) et l’env (dev).
RévisionUne version figée d’un service Cloud Run. Chaque déploiement en crée une nouvelle.
Service accountIdentité d’un programme (ici : le build, le front, le back), avec ses propres droits.
