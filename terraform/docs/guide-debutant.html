Guide débutant · terraform/ de ce repo · environnements dev et stg

Terraform, c’est une liste de courses pour le cloud.

Tu ne cliques plus dans la console Google Cloud. Tu décris ce que tu veux dans des fichiers, et Terraform se charge de créer, modifier ou (presque jamais) détruire pour coller à cette description. Ce guide utilise exactement le Terraform de PIM Accor enrichment.

1. L’idée, en une image mentale

Imagine un hôtel. Toi, tu tiens le planning des chambres : « je veux une réception ouverte au public (le front), un back-office réservé au personnel (le back), deux casiers où l’on dépose les fichiers (PIM d’un côté, Expedia / Booking de l’autre), un local à bagages (les images Docker) et un coffre pour les clés (le state) ». Terraform compare ce planning à l’hôtel réel (Google Cloud), puis fait uniquement les travaux nécessaires.

Terraform n’est pas un script « crée un bucket, puis un service, puis… ». C’est un rapprochement : « la réalité doit ressembler à ces fichiers ». Si tu relances un apply sans rien changer, il dit : No changes. C’est le bon signe.

2. Trois commandes, toujours les mêmes

init

Prépare le dossier : télécharge le provider Google et se branche sur le bon carnet de state (dev ou stg). À refaire à chaque fois que tu changes d’environnement.

plan

Montre le diff, sans toucher au cloud. « Je vais créer X, modifier Y, détruire Z. » Lis-le toujours, surtout la ligne destroy.

apply

Exécute le plan. Après, le cloud et le state sont à jour.

Dans ce repo, un Makefile enchaîne ces commandes pour toi. Tu choisis l’environnement avec ENV=dev ou ENV=stg : 

# depuis le dossier terraform/
make init  ENV=dev     # se branche sur le state de dev
make plan  ENV=dev     # calcule le diff et l’enregistre dans core/tfplan_dev
make apply ENV=dev     # applique exactement ce plan
make output ENV=dev    # relit les URLs, noms de buckets…

make init plan ENV=stg && make apply ENV=stg

Derrière, le Makefile lance simplement :

terraform -chdir=core init -reconfigure -backend-config=../config/terraform_dev_backend.hcl
terraform -chdir=core plan  -var-file=../vars/global.tfvars -var-file=../vars/dev.tfvars -out=tfplan_dev
terraform -chdir=core apply tfplan_dev

-chdir=core veut dire « travaille comme si tu étais dans core/ ». -backend-config choisit le carnet de state, et les deux -var-file choisissent les réglages.

make vient avec les outils en ligne de commande d’Apple (xcode-select --install s’ils manquent). Tu peux aussi taper directement les commandes terraform ci-dessus.

3. À quoi sert chaque type de fichier

Terraform lit tous les .tf d’un dossier et les fusionne. Découper en plusieurs fichiers, c’est juste pour les humains. Clique un onglet :

Le contrat d’outillage

Quelle version de Terraform, quel plugin cloud. Ici : Terraform ≥ 1.9, provider Google ~> 8.5 (toute 8.x à partir de 8.5). Le fichier .terraform.lock.hcl fige la version exacte téléchargée : il se commite.

terraform {
  required_version = ">= 1.9"
  required_providers {
    google = { source = "hashicorp/google" version = "~> 8.5" }
  }
}

Où est rangé le carnet de bord

Le state n’est pas dans Git : il vit dans un bucket GCS. core/backend.tf est volontairement vide (« backend partiel ») : c’est le fichier config/terraform_<env>_backend.hcl passé à init qui dit dans quel « dossier » (prefix) du bucket écrire. 

# core/backend.tf
terraform {
  backend "gcs" {}
}

# config/terraform_dev_backend.hcl
bucket                      = "bkt-cvto-accor-pim-enrichment-dev-euw1-tfstate"
prefix                      = "core/dev"   # stg : "core/stg"
impersonate_service_account = "sa-dev-terraform@…"

Comment parler à Google Cloud

Le provider est le traducteur. Ici il impersonne un service account Terraform : toi tu lances la commande, lui agit dans GCP. default_labels colle automatiquement les mêmes étiquettes (client, env, owner…) sur toutes les ressources. 

provider "google" {
  project                     = var.project_id
  region                      = var.region
  impersonate_service_account = var.terraform_service_account
  default_labels              = local.labels
}

Les paramètres (le « formulaire »)

On déclare quels réglages existent, leur type, parfois une valeur par défaut ou une règle de validation. On n’y met pas les valeurs d’un environnement précis. 

variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "stg"], var.env)
    error_message = "env doit valoir dev ou stg."
  }
}

Les valeurs, en deux étages

vars/global.tfvars contient ce qui est commun (projet, région, client = "accor", solution = "pim-enrichment", liste des APIs). vars/dev.tfvars et vars/stg.tfvars contiennent ce qui change d’un environnement à l’autre. Si une valeur existe dans les deux, le second fichier gagne. 

# vars/dev.tfvars
env                      = "dev"
manage_project_resources = true
deploy_branch            = "dev"   # chaque push sur dev déploie cet env
front_public             = true

Les tags d’image n’apparaissent plus ici : c’est la CI (Cloud Build) qui choisit l’image déployée.

Ce qu’on veut obtenir

core/main.tf ne crée presque rien directement : il appelle des modules (un bucket, un Cloud Run, des APIs…) en leur passant des arguments. Le bloc locals calcule les noms une seule fois pour tout le fichier. 

locals {
  base = "cvto-${var.client}-${var.solution}-${var.env}-${var.region_short}"
  # dev → cvto-accor-pim-enrichment-dev-euw1
}

Ce qu’on veut afficher après un apply

Les URLs front et back, les noms des buckets, les emails des service accounts… Tu les relis avec make output ENV=dev.

Les raccourcis

Le Makefile n’est pas du Terraform : c’est un aide-mémoire exécutable. Il évite de se tromper de fichier de backend ou de vars entre dev et stg. Cibles utiles : init, plan, apply, output, fmt, validate.

4. Comment ce projet est structuré

Un seul plan d’immeuble (core/), des pièces types réutilisables (modules/), et pour chaque environnement : un carnet (config/) et des réglages (vars/).

plan
core/

Le module racine, celui qu’on lance. Il décrit tout un environnement : APIs, dépôt d’images, service accounts, 2 buckets de fichiers, Cloud Run back et front. Il ne contient aucune valeur propre à dev ou stg.

pièces
modules/

Recettes génériques : apis, artifact_registry, cloud_run, cloud_storage, iam. Jamais lancées seules : core les appelle.

réglages
vars/

global.tfvars (commun) + dev.tfvars / stg.tfvars (spécifique).

carnets
config/

Un fichier backend par environnement : il pointe vers core/dev ou core/stg dans le bucket de state.

Cloud Run back gcr-cvto-accor-pim-enrichment-dev-euw1-back L’API, privée : seul le front peut l’appeler

En stg, c’est exactement la même liste avec stg à la place de dev.

Un module n’a pas de backend. Ce n’est pas un projet, c’est une fonction que core appelle : « fabrique-moi un Cloud Run avec ces arguments ».

5. Un plan, deux environnements

dev et stg sont construits avec le même code. Seuls changent les réglages (vars/) et le carnet (config/). Les deux vivent dans le même projet GCP ; les noms (…-dev-… / …-stg-…) et les states séparés les empêchent de se marcher dessus.

core/ (même code) + vars/dev.tfvars + config/…dev_backend.hcl → dev
core/ (même code) + vars/stg.tfvars + config/…stg_backend.hcl → stg
EnvironnementPréfixe du stateURL du front
dev core/dev gcr-…-dev-euw1-front…run.app
stg core/stg gcr-…-stg-euw1-front…run.app

Les ressources uniques au projet n’ont qu’un seul propriétaire. Le bucket de state et le rôle roles/run.admin du SA Terraform n’existent qu’en un exemplaire. Si dev et stg les géraient, détruire stg les supprimerait aussi pour dev. Ils sont donc créés avec count = var.manage_project_resources ? 1 : 0, et seul dev.tfvars met manage_project_resources = true.

Piège classique : make plan ENV=stg juste après avoir travaillé sur dev, sans refaire make init ENV=stg. Terraform comparerait alors les réglages stg au carnet de dev. Le Makefile fait un -reconfigure à chaque init : relance-le à chaque changement d’environnement.

6. Resource, variable, local, module : le vocabulaire

MotEn françaisIci
variable Entrée paramétrable var.deploy_branch, var.env
locals Calculs internes (noms, chemins) local.base → cvto-accor-pim-enrichment-dev-euw1
resource Objet cloud créé / géré bucket, API, service account, Cloud Run (dans les modules)
module Sous-dossier réutilisable module "cloud_run_front" et module "cloud_run_back" utilisent tous deux ../modules/cloud_run

depends_on « Attends que ça existe » Activer l’API Run avant de créer les services
for_each Une ressource par élément d’une liste Une API Google par entrée de var.apis

Dans core/main.tf, un appel de module ressemble à un appel de fonction :

module "cloud_run_back" {
  source = "../modules/cloud_run"

  name                  = "gcr-${local.base}-back"
  image                 = local.placeholder_image   # image de démarrage, ensuite gérée par la CI
  service_account_email = module.iam.emails["back"]
  invoker_members       = [module.iam.members["front"]]   # seul le front peut l’appeler

  env = {
    PIM_FILES_BUCKET = module.bucket_pim_files.name
    OTA_FILES_BUCKET = module.bucket_ota_files.name
  }
}

Le même module sert au front, avec d’autres arguments : invoker_members = ["allUsers"] quand front_public = true (n’importe qui peut ouvrir l’URL ; plus tard, IAP ou une authentification applicative), et une variable BACKEND_URL qui reçoit l’URL du back.

Les modules vérifient aussi la convention de nommage : un nom de Cloud Run qui ne commence pas par gcr- ou un bucket avec un underscore font échouer le plan avant même de contacter Google.

7. Qui a le droit de faire quoi (les 4 identités)

Il y a plusieurs « robots » distincts. Les mélanger, c’est la source n°1 de confusion.

IdentitéÀ quoi elle sert
sa-dev-terraform@… Terraform lui-même, pour dev comme pour stg. Il crée les buckets, les Cloud Run et pose l’IAM. Ton compte humain doit seulement pouvoir l’impersonner (roles/iam.serviceAccountTokenCreator).
sa-<env>-frontend@… Le conteneur front en train de tourner. Son seul droit : roles/run.invoker sur le back de son environnement, pour pouvoir l’appeler.
sa-<env>-backend@… Le conteneur back. Il a roles/storage.objectAdmin (lire, écrire, supprimer des fichiers) sur les buckets PIM et OTA de son environnement, et rien d’autre.
sa-<env>-cloudbuild@… La CI. Pousse les images dans l’Artifact Registry de son env et publie de nouvelles versions de ses 2 Cloud Run (voir le guide CI/CD).

Les droits du SA Terraform ont été donnés par l’admin du projet (editor, projectIamAdmin, serviceAccountUser…). editor ne suffit pas pour rendre un Cloud Run public : le code ajoute donc roles/run.admin (variable terraform_sa_extra_roles, gérée par dev). Le rôle serviceAccountUser au niveau projet lui permet de déployer un Cloud Run « en tant que » les SA front et back.

8. Le state : le carnet de ce que Terraform « possède »

Après un apply, Terraform écrit un JSON (le state) : IDs des ressources, attributs, dépendances. Sans ce fichier, il ne sait plus que ce bucket-là est « le sien » et risquerait d’en créer un second.

D’où le bucket bkt-cvto-accor-pim-enrichment-dev-euw1-tfstate : versionné (les 20 dernières versions de chaque state sont gardées), accès public bloqué, et force_destroy = false (impossible de le supprimer tant qu’il contient des states). Il range un carnet par environnement : core/dev/default.tfstate et core/stg/default.tfstate.

Le paradoxe de l’œuf et de la poule. Le bucket de state est géré par Terraform, mais Terraform a besoin du bucket pour stocker son state. Comment on s’en est sorti :

  1. une petite couche temporaire (« bootstrap ») a créé le bucket avec un state local, sur le disque ;
  2. une fois core en place, on a importé le bucket dans le state core/dev (bloc import) : Terraform l’a adopté sans le recréer ;
  3. la couche bootstrap a ensuite été supprimée. Elle n’est plus nécessaire.

Importer, c’est dire à Terraform : « cette ressource existe déjà, c’est désormais toi qui la gères ». C’est aussi comme ça qu’on a gardé l’Artifact Registry et le SA du front existants lors de la réorganisation.

9. Et le déploiement de l’application ?

Il ne passe plus par Terraform ni par un script : chaque push sur la branche dev ou stg déclenche Cloud Build, qui construit l’image et la met en ligne. Terraform crée les Cloud Run et les triggers, puis ignore l’image qui tourne (lifecycle.ignore_changes) pour ne jamais annuler un déploiement.

push sur dev → trigger Cloud Build → build + push Artifact Registry → Cloud Run nouvelle révision

Tout est expliqué dans le guide CI/CD Cloud Build.

Convention de noms

TypeFormatExemple
Cloud Run gcr-cvto-[client]-[solution]-[env]-[region]-[service] gcr-cvto-accor-pim-enrichment-dev-euw1-front
Bucket bkt-cvto-[client]-[solution]-[env]-[region]-[purpose] bkt-cvto-accor-pim-enrichment-dev-euw1-ota-files
Artifact Registry ar-cvto-[client]-[solution]-[env]-[region]-docker ar-cvto-accor-pim-enrichment-stg-euw1-docker
Service account sa-[env]-[rôle] sa-stg-backend (un SA GCP a 30 caractères max)

Règles : minuscules, chiffres et tirets uniquement, 63 caractères max. Exception pratique : Cloud Run (API v2) refuse au-delà de 49 caractères, le module le vérifie.

Mini check-list débutant

  1. gcloud auth login puis gcloud auth application-default login
  2. make init ENV=… à chaque changement d’environnement
  3. Toujours plan avant apply, et lire la ligne « to destroy »
  4. Le code applicatif se déploie par un push Git, pas par Terraform
  5. Ne pas mettre le state dans Git ; ne pas détruire le bucket tfstate
  6. Un apply n’est pas « relancer le serveur » : s’il n’y a pas de diff, rien ne change
